# ChangeSafe v0.1.0 Demo Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a reproducible v0.1.0 verification snapshot and a one-command live-first presentation runner that falls back only for live-stage availability failures, signs every demonstrated verdict, verifies it against a trusted public key, and remains fully usable offline after dependency installation.

**Architecture:** Keep the deterministic policy and receipt authority in the existing CLI and `@changesafe/core`. Small release scripts invoke the built CLI, add release-specific preflight/timeout/manifest orchestration, and never reproduce policy, receipt-hash, or signature-verification logic. The official key ceremony happens only on the FileVault-enabled presentation MacBook; tests use disposable keys and never persist them.

**Tech Stack:** Node.js 22, npm 10.9.8, strict TypeScript, ESM `.mjs` release scripts, Zod 4, Vitest 4, Ed25519/Web Crypto, GitHub Actions on Ubuntu.

## Global Constraints

- Node 22 is the sole supported runtime major; `engines.node` is `>=22 <23`.
- npm is exactly `10.9.8`; `packageManager` is `npm@10.9.8`.
- CI and release rehearsal install with `npm ci`; neither may modify `package-lock.json`.
- GitHub Actions caches npm package downloads only and never caches `node_modules`.
- The default presentation attempt is OpenAI `gpt-5.6`, exactly once, with a 30-second wall-clock deadline and no retry.
- Missing credentials, network/provider failure, timeout, malformed output, schema failure, or ungrounded evidence may select the captured fixture exactly once.
- A valid live `BLOCK` is a successful safety verdict; it is signed and verified and never triggers fallback.
- Fixture validation, deterministic gate, receipt creation/signing, key mismatch, hash mismatch, or signature failure is a hard stop with exit code 2 and never triggers fallback.
- `--offline` crosses no provider-selection or network boundary and must pass with credentials removed and guarded `fetch`, HTTP, HTTPS, socket, and DNS surfaces.
- The offline guarantee starts only after dependencies have been installed.
- Official private-key material never enters Git, CI configuration, logs, screenshots, release artifacts, shell history, or cloud-synchronized storage.
- Official live receipts are temporary files and never enter `verification/v0.1.0/`.
- OIDC, the decision server, and the ledger are absent from the presentation execution path.
- The demo never approves and never executes infrastructure; decisions are only `gate_only` or `blocked`.
- `verification/v0.1.0/` becomes immutable when tag `v0.1.0` exists; later corrections use a new versioned directory.
- Ubuntu CI is the automated reference environment; the actual presentation MacBook must pass the manual rehearsal gate.

### Shared process result

The release scripts use one stable subprocess result:

```js
/**
 * @typedef {{
 *   code: number | null,
 *   signal: NodeJS.Signals | null,
 *   stdout: string,
 *   stderr: string,
 *   timedOut: boolean
 * }} CommandResult
 */
```

No release script prints `stderr` from a live provider call. Tests may inspect
synthetic error strings, but production output contains only the sanitized
categories `credential_missing`, `timeout`, `provider_unavailable`, or
`model_output_invalid`.

Implement `sha256File` over raw bytes and fingerprint the public key exactly
as core does:

```js
export function publicKeyIdFromPem(pem) {
  const spki = createPublicKey(pem).export({ type: "spki", format: "der" });
  return createHash("sha256").update(spki).digest("hex").slice(0, 32);
}

export async function sha256File(file) {
  return createHash("sha256").update(await readFile(file)).digest("hex");
}

export function canonicalJson(value) {
  if (value === null || typeof value !== "object") return JSON.stringify(value);
  if (Array.isArray(value)) {
    return `[${value.map((entry) => canonicalJson(entry)).join(",")}]`;
  }
  return `{${Object.entries(value)
    .sort(([left], [right]) => (left < right ? -1 : left > right ? 1 : 0))
    .map(([key, entry]) => `${JSON.stringify(key)}:${canonicalJson(entry)}`)
    .join(",")}}`;
}

export function sha256Text(text) {
  return createHash("sha256").update(text, "utf8").digest("hex");
}
```

- [ ] **Step 4: Implement a bounded, capture-only subprocess wrapper**

`runCommand` must use `spawn`, collect stdout/stderr, kill on timeout, and
return `CommandResult`; it must never log its command or arguments:

```js
export function runCommand(file, args, {
  cwd,
  env = process.env,
  timeoutMs = 0,
} = {}) {
  return new Promise((resolve, reject) => {
    const child = spawn(file, args, { cwd, env, stdio: ["ignore", "pipe", "pipe"] });
    let stdout = "";
    let stderr = "";
    let timedOut = false;
    const timer = timeoutMs > 0
      ? setTimeout(() => {
          timedOut = true;
          child.kill("SIGTERM");
        }, timeoutMs)
      : null;
    child.stdout.setEncoding("utf8");
    child.stderr.setEncoding("utf8");
    child.stdout.on("data", (chunk) => { stdout += chunk; });
    child.stderr.on("data", (chunk) => { stderr += chunk; });
    child.once("error", reject);
    child.once("close", (code, signal) => {
      if (timer) clearTimeout(timer);
      resolve({ code, signal, stdout, stderr, timedOut });
    });
  });
}
```

Import `spawn` from `node:child_process`. Add a `ReleaseVerificationError`
whose public message contains only the failed check name.

- [ ] **Step 5: Implement `verifyBundle` as an ordered hard-stop pipeline**

The function must:

1. parse `provenance.json` with `VerificationManifestSchema`;
2. remove `manifestSha256`, serialize the remaining manifest with recursively
   sorted object keys, and verify its SHA-256 before trusting any metadata;
3. require exactly the protected filenames plus `provenance.json`;
4. recompute every raw file hash and compare it to the manifest;
5. recompute `demo.pub.pem` fingerprint and compare it to both
   `fingerprint.txt` and `manifest.publicKeyId`;
6. parse the signed envelope and cross-check its receipt id, timestamps,
   source id, app/policy versions, fixture provenance, model, and signature
   key id against the manifest;
7. run the existing CLI gate over `input.json` and `replay-fixture.json` into
   a temporary bare receipt using the official id/time;
8. deep-compare that regenerated receipt to the envelope's receipt;
9. run the existing CLI `verify` with the input, replay fixture, and trusted
   public key; and
10. when `compareTag` is true and `refs/tags/v0.1.0` exists, compare each
    bundle file byte-for-byte with `git show v0.1.0:<path>`.

The gate invocation is:

```js
[
  CLI,
  "gate",
  "--domain", "network",
  "--input", inputPath,
  "--proposal", fixturePath,
  "--source-id", SOURCE_ID,
  "--receipt", replayedReceiptPath,
  "--receipt-id", RECEIPT_ID,
  "--created-at", manifest.receiptCreatedAtUtc,
  "--format", "json",
]
```

Accept gate exit `0` or `1`; reject exit `2` or a missing receipt. The CLI
verification invocation is:

```js
[
  CLI,
  "verify", signedReceiptPath,
  "--domain", "network",
  "--input", inputPath,
  "--proposal", fixturePath,
  "--public-key", publicKeyPath,
  "--format", "json",
]
```

Only exit `0` is valid. Parse its JSON and require `ok === true` and
`signature.verdict === "valid"`.

- [ ] **Step 4: Implement the one live attempt**

For non-offline mode, invoke:

```js
[
  CLI,
  "analyze",
  "--domain", "network",
  "--input", INPUT,
  "--provider", "openai",
  "--model", model,
  "--out", liveProposal,
  "--receipt", liveReceipt,
  "--sign-key", signingKey,
  "--source-id", SOURCE_ID,
  "--format", "json",
]
```

Set `timeoutMs: 30_000`. Do not retry. Exit `0` and exit `1` both mean a
valid deterministic verdict if proposal and signed receipt exist. Never use
captured fixture provenance for a live receipt.

The presence of `liveProposal` is the boundary marker because `runAnalyze`
writes it only after provider structured output, local Zod validation, and
evidence cross-checking succeed, and before deterministic gating/signing.
Therefore:

- no proposal file plus exit `2`, signal, or timeout is a live-stage
  availability/validation failure and may fall back;
- a proposal file plus exit `2`, signal, timeout, or missing signed receipt is
  a downstream safety failure and must hard-stop; and
- exit `0` or `1` plus both files continues to public-key verification.

On a genuine live-stage failure, delete any partial receipt, select one
sanitized fallback category, print `LIVE unavailable → FALLBACK (category)`,
and proceed exactly once.

const http = require("node:http");
const https = require("node:https");
const net = require("node:net");

const denied = (surface) => function deniedNetworkCall() {

            --out "$RUNNER_TEMP/v0.1.0-ci-key" --format json > "$RUNNER_TEMP/keygen.json"
