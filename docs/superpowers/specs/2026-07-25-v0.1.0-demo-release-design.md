# ChangeSafe v0.1.0 Demo Release Design

**Status:** Approved design, written 2026-07-25  
**Branch:** `release/v0.1.0-demo`  
**Base:** `main` at `d89e6a87dbb7c3994fbcbdb7565bb2e300e6a602`

## 1. Goal

Prepare a GitHub-first v0.1.0 release that demonstrates ChangeSafe as a
deterministic airlock with one reliable command:

1. attempt one GPT-5.6 live analysis;
2. fall back immediately to a captured fixture when the live stage is
   unavailable or invalid;
3. run the deterministic gate;
4. sign the resulting receipt with a dedicated Ed25519 demo key; and
5. verify the receipt against a trusted public key.

The release must remain demonstrable without network access after dependencies
have been installed, and a public verification bundle must let anyone verify
the official v0.1.0 snapshot without possessing the private key.

## 2. Scope

### Included

- A versioned, immutable public verification bundle under
  `verification/v0.1.0/`.
- A one-command presentation runner with a default live-first mode and an
  explicit `--offline` mode.
- A 30-second hard timeout for the one live model attempt.
- Immediate fixture fallback for live-stage availability or validation
  failures.
- Hard stops for deterministic gate execution errors, receipt signing errors,
  snapshot integrity errors, and public-key verification errors.
- Node 22 as the sole supported runtime major for v0.1.0.
- npm 10.9.8 as the exact package-manager version.
- Ubuntu GitHub Actions as the automated reference environment and the
  presentation MacBook as a required manual release rehearsal environment.
- CI validation of the verification bundle, offline contract, runtime
  contract, and existing project quality gates.

### Excluded

- OIDC authentication, the decision server, and the append-only ledger in the
  live presentation flow. They may appear in architecture explanations only.
- Windows support for v0.1.0.
- Offline cloning, dependency download, or package installation.
- Committing, uploading, or injecting the demo private key into CI.
- Automatic approval or infrastructure execution.
- Storing non-deterministic live receipts in the immutable public snapshot.
- Retrying a failed live model call.

The permanent repository safety invariants remain controlling. The demo never
executes a change and never allows model output to decide approval or risk.

## 3. User-Facing Commands

The release exposes one npm entry point:

```bash
npm run demo:v0.1.0
```

The default command runs preflight, makes one live GPT-5.6 attempt, and uses
the captured fixture immediately if that attempt cannot produce a locally
validated proposal within 30 seconds.

The guaranteed network-free path is:

```bash
npm run demo:v0.1.0 -- --offline
```

Both paths require the dedicated private key to be supplied out of band:

```bash
export CHANGESAFE_DEMO_SIGNING_KEY=/absolute/path/to/changesafe-v0.1.0-demo.pem
```

The runner never prints the environment variable value, private-key content,
or a command line containing private-key content. The public key is loaded from
`verification/v0.1.0/demo.pub.pem`.

The official public snapshot can be verified without the private key:

```bash
npm run verify:v0.1.0
```

This command verifies the manifest, canonical receipt hash, input hash,
proposal hash, public-key fingerprint, and Ed25519 signature.

## 4. Architecture

### 4.1 Presentation runner

The runner is orchestration around existing ChangeSafe capabilities, not a
second policy engine:

- live proposal generation uses the existing provider adapter and local Zod
  validation;
- fixture parsing uses the production domain schemas;
- both live and fixture proposals enter the existing `gateParsedProposal`
  path;
- receipt creation and signing use `@changesafe/core`;
- receipt verification uses the existing CLI verification path.

The runner owns only preflight, timeout, path selection, temporary output
management, and presentation-safe status messages. It must not duplicate
policy logic, receipt hashing, signature verification, or risk derivation.

### 4.2 Live path

The default path is:

```text
preflight
  → one OpenAI GPT-5.6 analysis attempt
  → provider structured output validation
  → local Zod and evidence-reference validation
  → deterministic gate
  → signed temporary receipt
  → public-key verification
```

The default provider/model pair is OpenAI GPT-5.6. The runner may accept an
explicit provider or model override for rehearsal, but the presentation
command and documentation use GPT-5.6.

An `AbortController` and process-level deadline enforce a 30-second wall-clock
limit over the complete live stage, including response receipt, parsing, and
local validation. There is no retry.

### 4.3 Fixture fallback path

The runner switches to the v0.1.0 captured fixture when the live stage fails
because of:

- missing or unusable provider credentials;
- DNS, connection, TLS, or other network failure;
- provider or model access failure;
- rate limiting or provider-side error;
- the 30-second timeout;
- malformed provider response;
- structured-output failure;
- local Zod validation failure; or
- invented or unknown evidence references.

Fallback is explicit, not silent. The screen and final structured result name
the selected path as `FALLBACK`, include a sanitized reason category, and name
the fixture provenance as `captured`.

The fallback path is:

```text
captured input + captured fixture
  → production schema validation
  → deterministic gate
  → signed temporary receipt
  → public-key verification
```

### 4.4 Strict offline path

`--offline` skips the live stage before provider selection, credential checks,
provider transport construction, or any external request. It uses the same
fixture, gate, signing, and verification operations as automatic fallback.

The offline implementation has a separate import and execution boundary from
the live adapter. Its tests install guards for the project's network surfaces
(`fetch`, HTTP/HTTPS requests, sockets, and DNS lookup) that fail immediately
if called. The offline runner must pass with all provider credentials removed
and with no reachable network.

The guarantee begins after a successful immutable dependency installation.
It does not cover `git clone`, npm registry access, or package download.

## 5. Failure Semantics

ChangeSafe distinguishes availability failure from safety failure.

| Condition | Behavior |
| --- | --- |
| Live credential, network, model, timeout, parsing, or model-output validation failure | Select fixture immediately; do not retry |
| A valid live proposal produces one or more `BLOCK` findings | Do not fall back; report the valid blocked verdict, sign it, and verify it |
| Fixture schema or evidence validation fails | Hard stop with exit code 2 |
| Deterministic gate cannot evaluate | Hard stop with exit code 2 |
| Receipt cannot be created or signed | Hard stop with exit code 2 |
| Trusted public key does not match the receipt key id | Hard stop |
| Receipt hash, input hash, proposal hash, manifest hash, or signature is invalid | Hard stop |
| `--offline` attempts network or provider access | Test failure and hard stop |

A policy `BLOCK` is a successful safety outcome, not a broken demo. The
presentation runner verifies and displays the blocked receipt before returning
a presentation-level success status. It must still preserve the underlying
gate verdict and never label the change approved.

No fixture path may conceal a failure that occurs after a proposal enters the
deterministic safety boundary.

## 6. Public Verification Bundle

The committed layout is:

```text
verification/v0.1.0/
  README.md
  input.json
  replay-fixture.json
  receipt.signed.json
  demo.pub.pem
  fingerprint.txt
  provenance.json
```

### 6.1 Contents

- `input.json` is a frozen, fictional, schema-valid copy of the selected
  network scenario input.
- `replay-fixture.json` is the frozen captured fixture used to generate the
  official result.
- `receipt.signed.json` is the canonical receipt envelope generated from
  those frozen artifacts with the v0.1.0 demo private key.
- `demo.pub.pem` is the corresponding Ed25519 public key.
- `fingerprint.txt` records the ChangeSafe key id, defined by core as the
  first 32 lowercase hexadecimal characters of SHA-256 over the SPKI public
  key.
- `provenance.json` records:
  - bundle version and schema version;
  - the source commit used to generate the bundle;
  - the one captured generation timestamp used by the official receipt;
  - scenario id, fixture provenance, provider, and model;
  - policy and application versions;
  - public-key id;
  - SHA-256 for every other file in the bundle; and
  - the verification command.
- `README.md` explains the trust boundary and verification steps without
  claiming that possession of the public key proves who published it.

### 6.2 Determinism boundary

The input, fixture, policy output, unsigned receipt payload, receipt hash, and
Ed25519 signature are deterministic when the fixed private key and captured
timestamp are used. The owner can reproduce the signed envelope byte for byte
with that private key.

Public users do not receive the private key and therefore do not regenerate
the official signature. They independently reconstruct and validate the
receipt payload from the public input and fixture, compare canonical hashes,
and verify the frozen signature against the separately recorded public key.
This is verification, not re-signing.

Live presentation receipts are written only to an operating-system temporary
directory. They use the same dedicated key but are not copied into
`verification/v0.1.0/` and are not represented as reproducible snapshots.

### 6.3 Immutability

The v0.1.0 directory is immutable after the `v0.1.0` release tag is created.
Corrections create a new versioned directory; they never rewrite this one.

Before the tag exists, CI validates the manifest and every cryptographic
relationship. After the tag exists, CI also compares
`verification/v0.1.0/` byte for byte with the tagged tree and rejects any
change.

The Git tag and repository history are the publication anchor. The public key
inside the same repository is sufficient for reproducible verification but is
not, by itself, an external identity proof. The published fingerprint should
also appear in presentation material and release notes.

## 7. Demo Key Lifecycle

- Generate one Ed25519 key pair before the presentation with
  `changesafe keygen`.
- Store the private key outside the repository and outside cloud-synchronized
  folders on the FileVault-enabled presentation MacBook.
- Keep permissions at `0600`; preflight rejects broader permissions.
- Commit only the public key and fingerprint.
- Use this key only for v0.1.0 official and presentation receipts.
- Do not place the private key in shell history, screenshots, terminal
  recordings, environment dumps, CI secrets, logs, or crash reports.
- If the private key is lost, keep the historical public bundle unchanged and
  issue future receipts under a newly versioned key.
- If compromise is suspected, stop using the key immediately. Publish a new
  versioned bundle and a supersession notice; never replace the old public key
  or signed snapshot in place.
- After the v0.1.0 presentation and release rehearsal window closes, remove
  the private key from the MacBook. Retain the public key, fingerprint,
  receipt, and provenance indefinitely so historical verification remains
  possible.

Deleting the private key prevents new signatures; it does not invalidate
existing signatures.

## 8. Runtime and Dependency Reproducibility

### 8.1 Runtime

- `.nvmrc` remains on Node 22.
- `package.json` narrows `engines.node` to `>=22 <23`.
- `package.json` records `packageManager: "npm@10.9.8"`.
- `package.json` records npm 10.9.8 in `engines.npm`.
- CI and macOS preflight explicitly install or activate npm 10.9.8 and fail
  if `npm --version` differs.
- Node 24 is removed from the v0.1.0 CI matrix.

The supported contract is the Node 22 major, not every historical or future
Node release. Preflight prints the exact Node 22 patch in use so the
presentation rehearsal is auditable.

### 8.2 Installation

CI and release rehearsal use:

```bash
npm ci
```

The install must not modify `package-lock.json`. A manifest/lockfile mismatch
is a release failure.

GitHub Actions uses npm's package-download cache keyed by the lockfile and
runtime. It does not cache `node_modules`. A cold cache must still succeed.

## 9. CI and Rehearsal

### 9.1 Ubuntu CI

The existing quality gate remains:

- lint;
- typecheck;
- unit and integration tests;
- production build;
- Playwright safe and blocked paths;
- client-bundle secret scan;
- CLI binary tests; and
- Terraform Action smoke.

The matrix collapses to Ubuntu with Node 22 and npm 10.9.8.

New release checks:

1. assert runtime and package-manager versions;
2. run immutable `npm ci`;
3. validate the provenance manifest schema and file hashes;
4. recompute the public-key fingerprint;
5. verify the signed receipt against the public key, input, and fixture;
6. prove that modified input, proposal, receipt, manifest, or public key is
   rejected;
7. run the presentation runner in `--offline` mode with an ephemeral
   CI-generated key;
8. assert the offline path never invokes the injected live runner or any
   guarded network surface;
9. assert live timeout/error selects fallback exactly once;
10. assert gate, signing, and verification failures never select fallback;
11. scan tracked files and build output for private-key material; and
12. after the release tag exists, assert the v0.1.0 directory is byte-identical
    to the tagged snapshot.

The ephemeral CI key tests mechanics only. It is never the official demo key
and is never persisted as an artifact.

### 9.2 Presentation macOS rehearsal

Release is blocked until the actual MacBook passes:

```bash
npm ci
npm run demo:v0.1.0 -- --offline
npm run demo:v0.1.0
npm run verify:v0.1.0
```

The rehearsal checklist records:

- exact Node 22 patch and npm 10.9.8;
- private-key file permission check;
- public-key fingerprint match;
- successful offline run with Wi-Fi disabled;
- one successful live run or a visibly correct automatic fallback;
- no private-key content in terminal output or saved logs;
- hard-stop behavior after intentionally substituting an invalid public key;
  and
- completion within the presentation time budget.

macOS rehearsal is a human-recorded release gate, not a second GitHub Actions
matrix.

## 10. Output and Provenance

Every presentation run prints a compact result containing:

- selected path: `LIVE`, `FALLBACK`, or `OFFLINE`;
- provider and model when live was attempted;
- sanitized fallback category when applicable;
- input id and proposal id;
- deterministic risk and policy findings;
- decision (`gate_only` or `blocked`, never `approved`);
- receipt id and temporary receipt path;
- signing-key fingerprint; and
- verification verdict.

The runner must not display raw provider errors if they can contain request
headers, tokens, URLs with credentials, model response bodies, or local key
paths. Detailed errors remain available only in tests with synthetic data.

## 11. Planned File Boundaries

Implementation should preserve focused responsibilities:

- `scripts/demo-v0.1.0.mjs` — presentation orchestration, timeout, fallback,
  preflight, and safe output.
- `scripts/verify-v0.1.0.mjs` — manifest and official snapshot verification.
- `verification/v0.1.0/*` — frozen public snapshot.
- `tests/integration/release-demo.test.ts` — live/fallback/hard-stop/offline
  orchestration tests.
- `tests/integration/verification-bundle.test.ts` — manifest, hash,
  fingerprint, signature, and mutation-rejection tests.
- `.github/workflows/ci.yml` — Node/npm pin, download cache, and release
  checks.
- `package.json` — runtime/package-manager contract and npm scripts.
- `.nvmrc` — Node 22 runtime major.
- `README.md`, `docs/DEMO_SCRIPT.md`, and
  `docs/RELEASE_NOTES_v0.1.0.md` — public command, trust boundary, rehearsal,
  and fingerprint documentation.

If implementation proves that a reusable helper belongs in `packages/cli`,
it may be extracted there, but policy evaluation and signing logic must remain
owned by their existing packages.

## 12. Acceptance Criteria

The v0.1.0 demo release is ready only when all of the following are true:

- `npm run demo:v0.1.0` completes a live GPT-5.6 attempt or visibly selects
  the captured fixture within 30 seconds.
- `npm run demo:v0.1.0 -- --offline` succeeds after dependencies are
  installed with all network access unavailable.
- Live-stage failures fall back once and only once; downstream safety failures
  hard-stop.
- A valid `BLOCK` result is signed and verified without being relabeled as an
  execution error or approval.
- The official public snapshot verifies from public files alone.
- Mutation of any protected snapshot component is detected.
- No official private key exists in Git, CI configuration, logs, or release
  artifacts.
- Node 22 and npm 10.9.8 are enforced in Ubuntu CI and macOS rehearsal.
- CI caches package downloads only and uses immutable installation.
- Existing deterministic gate, replay, red-team, build, and e2e gates remain
  green.
- OIDC and ledger code are not required by the presentation command.
- The release notes and presentation material publish the same public-key
  fingerprint recorded in the bundle.
